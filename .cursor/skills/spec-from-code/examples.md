# コードから仕様を書く例

## What — 振る舞いで書く（良い例）

コード: 未ログインかつ `YYSpot` のとき 4個目ボタンを `null` で返す

```markdown
## 実現内容（What）

未ログインかつ画面上部チップが「わいわいスポット」ON のとき、下部ナビ 4個目ボタンは表示しない。
```

## What — How をコピーしない（悪い例）

```markdown
## 実現内容（What）

`!userId && activeMapMode === 'YYSpot'` のとき `fourthButton` を `null` にする。
```

→ 実装詳細。ユーザー視点・画面の振る舞いで書き直す。

## Why — 推測を明示する

コードだけでは意図が読み取れない場合:

```markdown
## 目的（Why）

（推測）未ログイン時にスタンプボタンを出すとタップしても利用できず混乱を招くため、非表示にする。

→ この理解で合っていますか？
```

ユーザー確認後、推測マークを外して確定する。

## 受入基準 — テスト観点から逆生成

既存テスト `BottomNavigationDock.test.tsx` がある場合、テスト名・assert を受入基準に変換する。

```markdown
## 受入基準

1. **未ログイン・わいわいスポット ON**: サインインせず `/home` を開き、画面上部チップが「わいわいスポット」ON のとき、下部ナビに「スタンプ」ラベルのボタンが存在しない。
```

## 既存仕様との矛盾

| 既存仕様                                 | コードの実際の振る舞い       |
| ---------------------------------------- | ---------------------------- |
| 未ログイン時スタンプを `disabled` で表示 | 未ログイン時スタンプを非表示 |

矛盾点を列挙したうえで、コードに合わせるか仕様どおりにコードを直すかをユーザーに確認する。

## 出力先の提案

| 状況                                     | 提案先                      |
| ---------------------------------------- | --------------------------- |
| 単一機能・受入基準が複数                 | `app/docs/spec/[機能名].md` |
| プロジェクト全体の概要                   | `README.md`                 |
| 既存仕様ファイルに `// 仕様:` リンクあり | リンク先ファイルを更新      |
