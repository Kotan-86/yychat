# バグ修正仕様を書く・更新する

仕様: docs/tools/prompts.md#基本的なcursorrules（小規模チーム向け）

## 記述ルール

- 現状（何が起きているか）と 期待される挙動（どうあるべきか）を必ず書く
- issue 番号を必ず書く
- 受入基準（デバッグ・回帰テスト基準）は測定可能・テスト可能な形で書く
- 根本原因（判明している場合）と修正アプローチ（What）を記録する
- How（具体的なソースコードの修正箇所）は書かない
- 曖昧な表現（「たぶん」「たまに」）を避け、再現条件を具体化する
- バグの仕様・検証基準を書く・更新するのみで、実装（コード修正）はしない

## 新規作成時

1. issue 番号 → 現象と再現手順（Why）→ 修正内容（What）→ 受入基準（再発防止テスト）の順に確認する
2. 再現条件の不明点は推測せずユーザーに質問する
3. GitHub Flavored Markdown で出力する

## 出力先

- バグ・不具合単位: `app/docs/spec/bugs/[issue番号_不具合概要].md`

## ワークフロー

### 新規作成

1. issue 番号・現象・再現手順・期待される挙動・受入基準をユーザーと確認する（不足があれば質問）
2. 下記テンプレートに沿って `app/docs/spec/bugs/[issue番号_不具合概要].md` を作成する
3. 実装・テスト・lint は行わない

### 既存仕様の更新（同じバグに対して調査が進んだ場合など）

1. 対象ファイルを読み、原因や再現条件、受入基準を更新する
2. `## 追記・変更理由` に今回の更新の背景（追加の調査結果など）を追記する
3. 実装・テスト・lint は行わない

## テンプレート

```markdown
# バグ修正: [不具合概要]

## Issue

#[番号]

## 不具合現象と再現手順（Why）

### 発生している現象

[どのような不具合が発生しているか、ユーザーやシステムへの影響]

### 再現手順

1. [手順 1]
2. [手順 2]
3. [期待値と実際の差異]

## 修正内容（What）

### 根本原因

[なぜこのバグが発生したか（ロジックの考慮漏れ、データ型の不一致など）]

### 修正方針

[どのような状態・挙動に変更するか。ユーザー視点やデータのあるべき姿で書く]

## 受入基準（再発防止・回帰テスト）

1. **[再現手順の検証]**: 再現手順を実行したとき、不具合が再現せず、期待される挙動（[具体的な内容]）になること。
2. **[影響範囲・回帰テスト]**: 今回の修正によって影響を受ける可能性がある [機能名/画面] が、従来どおり正常に動作すること。

## 関連するコンポーネント・機能

- [関連 UI / API / 既存の機能仕様書へのリンク]

## 変更・追記理由（更新時のみ）

- issue #[番号]: [仕様を更新した理由や、追加で判明した原因など]
```
