# 【ADR】発言支援ロジックの外部ライブラリ化方針

## Status

承認(accepted)

## Context

- プロトタイプで検証した発言支援（入力途中からの確定読み上げ＋効果音）を、既存の音声認識アプリへ組み込みたい
- 長期的な候補は **YY文字起こし** と **YYProbe**（いずれも **UIKit**）だが、入力 UI や送信フローの差分が未知のため、初回は片方に絞る（[ADR: Swift での開発フレームワーク](ADR_swift-framework.md)）
- ホスト側はすでに音声認識・チャット UI・（送信時の）読み上げを持つ。今回持ち込みたいのは **発言支援のロジック中心** であり、画面見た目は既存アプリに寄せる
- プロトタイプは **MVVM＋Feature プラグイン** で整理済みである（[ADR: アーキテクチャリファクタリング](ADR_architecture-refactoring.md)）。組み込み後もこの分離を崩したくない
- 入力読み上げは **方式A（確定読み＋デバウンス＋効果音）** を製品方針とする（[ADR: 入力読み上げ方式](ADR_feature-reads-method.md)）。方式Bは製品ライブラリの対象外とする
- ホスト実装者は、「どのデータを渡せば方式Aが動くか」が分かれば足りるようにしたい。Feature 向けの内部イベント組み立てをホストに要求したくない
- タイムライン画面仕様（[timeline-screen.md](timeline-screen.md)）は、認識と合成を同一画面に統合するプロダクト案であり、**ライブラリの配布境界そのものではない**
- 本 ADR は、ライブラリの **Why／What（境界・契約）** を決める。実装手順（How）は書かない

## Decision

### 配布物の定義（成果物スコープ）

#### 採用する成果物

**方式A（確定読み＋デバウンス＋効果音）つまり、案B**

- TTS エンジンから入力事実の受け取り・デバウンス確定読み・効果音・読み上げ状態の通知までをセットで配布する
- View／Storyboard／タイムライン UI は含めない
- 音声認識（YYAPIs 等）は含めない

#### 比較検討

| 案                                        | 中身                                   | 判定                                                                                                       |
| ----------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **A. TTS エンジンのみ**                   | 読み上げ再生・停止など                 | **不採用** — 方式A（デバウンス・効果音排他・IME 連動）をホストが再実装することになり、開発コストが高くなる |
| **B. 方式Aまでの発言支援 SDK（UI なし）** | ViewModel／Feature／Speech／効果音まで | **採用**                                                                                                   |
| **C. 下書き・送信ルールまで含む**         | B に加え下書き蓄積や Return 送信規約   | **不採用** — UIは既存音声認識アプリに寄せるため                                                            |

### 初回の組み込み先ホスト

#### 採用する方針

**初回の組み込み検証・受入の対象ホストは YY文字起こし に限定する**

- YYProbe への拡大は本 ADR の初回スコープ外とし、将来の担当者・別判断に委ねる
- 公開 API は特定アプリ名に依存させない（将来 YYProbe 等へ広げやすい契約を維持する）
- ただし初版の受入・スパイク・設定併存の確認は YY文字起こし 上で行えば足りる

#### 比較検討（記録）

| 案                                            | 内容                                     | 判定                                                         |
| --------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------ |
| **初回から YY文字起こしと YYProbe の両方**    | 同一 API で足りるかも含め同時検証        | **不採用** — 入力 UI／送信フロー差分が未知のまま範囲が広がる |
| **初回は YY文字起こしのみ（YYProbe は将来）** | 検証対象を絞り、API はアプリ非依存に保つ | **採用**                                                     |

### アーキテクチャ境界: MVVM の維持

#### 採用する構造

**ライブラリ内に ViewModel＋Feature（方式A）を置き、ホスト View は入力通知の中継に限定する**

> 入力通知...ホストが渡す未分類の入力（現在テキスト＋IME未確定か等）

- [ADR: アーキテクチャリファクタリング](ADR_architecture-refactoring.md) の依存方向を維持する
  - ホスト View（UIKit）→ ライブラリのホスト向け API（入力通知・結果通知）
  - ライブラリ内部で ViewModel が入力通知をドメインイベントへ翻訳し、Feature が読み上げ・効果音の副作用を担う
- ViewModel をホストに残さない — 方式Aの保証をライブラリ側に残し、ホスト差分は薄い アダプター層 に閉じる

#### 比較検討（記録）

- **ViewModel をホストに残し、ライブラリは TTS／副作用部品のみ** — ホストで実装できる範囲は広いが、方式Aの品質がホスト実装に依存するため不採用

### ホスト向け公開面（公開 API の契約）

#### 採用する公開面

**ホストが見るのは「View が ViewModel に渡す入力通知」に相当する入口と、結果を反映するための最小の結果通知だけとする**

ホスト実装者が知る必要があるのは次のみとする。

**入力（ホスト → ライブラリ）**

- テキスト変化時: 現在テキスト＋IME 未確定かどうか
- 必要なら: Return／送信相当の押下
- （任意）効果音の差し替え指定 — 役割単位（打鍵／削除など）で、既定アセットの代わりに使う音を渡せる
- 分類（変換中の増減か、確定テキスト変化か）はライブラリ内の ViewModel が行う。ホストは組み立てない

**出力（ライブラリ → ホスト）**

- 入力欄を空にしてほしい旨（クリア要求、または表示状態としての空テキスト）
- 読み上げ対象になった文字列（下書き／履歴への反映はホスト）
- 読み上げ中かどうか（ホストが既存仕様どおり認識のストップ／再開に使う）

**配線**

- セッション生成・Feature の bind はライブラリ内（Composer 相当）で完結させる
- ホストは「セッションを作り、事実を渡し、結果を購読する」だけで方式Aが動くことを目標とする
- 効果音を差し替えない場合でも、既定アセットで方式Aが完結すること

#### 公開しないもの

- Feature が購読するドメインイベント（プロトタイプの `TextAreaInputEvent` / `events` ストリーム）
- 各 Feature クラス、`InputScreenFeaturePlugin`、Speech／効果音プレイヤーの実装詳細
- タイムライン用のメッセージ列、音声認識関連 API
- 効果音ファイルの内部パスやバンドル構造を、ホスト必須の契約にすること（差し替えは公開 API 経由に閉じる）

#### 比較検討（記録）

- **Feature 向け `events` をホストに公開する** — ホストが内部イベントを組み立てることになり、「データを渡せば動く」から外れるため不採用
- **プロトタイプの ViewModel 型をそのまま広く public にする** — 内部拡張のたびにホストが壊れやすく、公開面が肥大するため不採用。ホスト向けは薄い入口に閉じる

### 方式A一本化と製品外機能

#### 採用する方針

**ライブラリの公開面・既定の発言支援は方式Aのみとする**

- Return／送信時の再読み上げはライブラリ既定の発言支援に含めない（タイムライン仕様とも一致）

### 既存の送信時読み上げとの関係

#### 採用する方針

**既存の「送信時の全文読み上げ」と、ライブラリの方式A（入力中の確定読み）は併存させる。設定で切り替え可能とする**

- 既存機能をライブラリ導入で置き換えて消さない
- ホスト製品の設定により、どちらの読み上げを使うか（またはどちらを有効にするか）を切り替えられること
- 送信時読み上げの実装・設定 UI はホスト側に残る。ライブラリは方式A側を提供する

#### 比較検討（記録）

| 案                         | 内容                                  | 判定                                                      |
| -------------------------- | ------------------------------------- | --------------------------------------------------------- |
| **置換のみ**               | 方式A導入後、送信時読み上げを廃止する | **不採用** — 既存ユーザーの使い方を奪う                   |
| **併存（設定で切り替え）** | 両方を残し、設定で選ぶ／切り替える    | **採用**                                                  |
| **常時両方有効**           | 入力中も送信時も常に読む              | **不採用** — 二重読み上げになりやすい。切り替え前提とする |

### ホストとの責務分担（What）

#### ライブラリが担うこと

- 方式Aに基づく確定テキストのデバウンス読み上げ
- IME 未確定中の効果音（既定アセット同梱。差し替えは次節）
- 読み上げ再生中の効果音抑制と、終了後の再開
- 読み上げ中も入力継続可能なこと（入力欄自体はホストが提供）
- 読み上げ状態（開始／終了）の通知
- 上記「出力」の通知

#### ホストが担うこと

- 既存 UIKit 入力 UI の提供と見た目
- 音声認識・録音・認識結果表示
- チャット／タイムライン等の会話ログ UI
- クリア要求・読み上げ済み文字列を自画面のルールに合わせて反映すること
- （任意）効果音の差し替え指定
- Audio Session の所有（カテゴリ設定・アクティブ化）
- 読み上げ中の音声認識ストップ／終了後の再開（既存 YY 系アプリの仕様に合わせる）
- 既存の送信時読み上げと方式Aの **設定による切り替え**（設定 UI・送信時読み上げ本体はホスト）

#### 読み上げ後の入力クリア

**ライブラリがクリアを要求し、ホストが入力欄を空にする**

- 既存チャットの入力欄ライフサイクルを壊しにくい
- ライブラリが特定の `UITextView` 所有や画面構造を前提にしない

### 効果音の同梱と差し替え

#### 採用する方針

**既定の効果音アセットをライブラリに同梱し、初版からホスト向け差し替え API を提供する**

- 何も指定しなければ、同梱アセットで方式Aの変換中フィードバックが鳴る
- ホストは役割単位（打鍵／削除など）で、既定の代わりに使う音を差し替えられる
- 差し替えは任意であり、未指定時に効果音が欠落してはならない

#### 比較検討（記録）

| 案                             | 内容                                     | 判定                                                     |
| ------------------------------ | ---------------------------------------- | -------------------------------------------------------- |
| **同梱しない**                 | 「音声合成のみ」に寄せられる             | **不採用** — 方式Aの体験がホストごとにバラつく           |
| **同梱のみ（差し替えなし）**   | セット再現はできる                       | **不採用** — YY 系アプリごとのブランド音に合わせられない |
| **同梱＋初版から差し替え API** | 既定体験を保ちつつホスト差分に対応できる | **採用**                                                 |
| **同梱＋差し替えは後続版**     | 初版の公開面は薄い                       | **不採用** — 初版組み込み時点で差し替え需要に応えたい    |

### Audio Session の所有権と認識との排他

#### 採用する方針

**Audio Session はホスト専有とする。ライブラリは `setCategory`／`setActive` を行わない**

- 組み込み先の YY文字起こし は、すでに録音用セッションを握っている（将来の YYProbe も同様の想定）
- ライブラリはアプリ共通セッション上で TTS／効果音を再生する前提とし、セッション設定はホストに任せる

**読み上げ中の音声認識ストップは、既存アプリ仕様に合わせホストが行う**

- 既存アプリでは「音声読み上げ中は音声認識がストップする」
- ライブラリに認識クライアントは含めないため、ストップ／再開の実行はホストが担う
- ライブラリは読み上げ状態を通知し、ホストがその通知を見て認識を止める／再開する

#### 比較検討（記録）

| 案                                                   | 内容                                         | 判定                                                  |
| ---------------------------------------------------- | -------------------------------------------- | ----------------------------------------------------- |
| **ホスト専有（ライブラリはセッションを設定しない）** | 認識アプリの既存セッション運用と衝突しにくい | **採用**                                              |
| **ライブラリも最小設定を行う**                       | 単体組み込みは簡単                           | **不採用** — ホストの認識設定と上書き合戦になりやすい |
| **ライブラリが認識のストップまで実行する**           | 排他を SDK 内で完結できる                    | **不採用** — 認識はホスト資産であり、ライブラリ境界外 |

### 配布形態

#### 採用する方針

**Swift Package（ソース配布）でライブラリとして配布する**

- 本 ADR が決めるのは「発言支援をライブラリ（SPM）として作る」ことまでとする
- YY文字起こしへの本番組み込み可否は、これからテストしたうえで別途判断する（本決定の必須結果ではない）
- UI／Storyboard を載せない方針と整合する

#### 比較検討（記録）

| 案                                        | 内容                                       | 判定                                                        |
| ----------------------------------------- | ------------------------------------------ | ----------------------------------------------------------- |
| **Swift Package（ソース配布）**           | 独立したライブラリとして開発・参照しやすい | **採用**                                                    |
| **同一リポジトリ内 Framework ターゲット** | 既存 YY 系の Framework 運用に合わせやすい  | **不採用** — まずはライブラリとして独立させることを優先する |
| **バイナリ XCFramework**                  | 配布形態を固定しやすい                     | **初期は採用しない** — 必要になったら別 ADR                 |

### ドキュメント境界

#### 採用する整理

- **本 ADR** — ライブラリ化の境界・ホスト向け契約・トレードオフ
- **[speech-support-sdk.md](speech-support-sdk.md)** — 方式Aの受入条件を、画面仕様から切り出して測定可能に書く。公開面（渡すデータ／受け取る結果）を受入基準に含める
- **[timeline-screen.md](timeline-screen.md)** — 統合画面プロダクトの仕様として残し、ライブラリ仕様と混同しない

## Consequences

### メリット

- 初回は YY文字起こし に絞ることで、組み込み検証の範囲が明確になる
- UI を押し付けずに発言支援を差し込める。ホストは「渡すデータと結果の購読」だけで方式Aが動く、という説明ができる
- Feature 向け内部イベントを公開しないため、ライブラリ内部の Feature 追加・変更がホストを壊しにくい
- MVVM＋方式Aという既存決定を、ライブラリ境界として再利用できる
- 公開 API をアプリ非依存に保てば、将来の YYProbe 拡大時にパッケージ分岐を避けやすい

### デメリット・トレードオフ

- 「音声合成のみ」という言葉より、実際の配布物（案 B）が広い。狭義 TTS／広義 SDK の言い分けが必要
- 効果音の差し替え API が初版の公開面に入るため、役割の粒度（打鍵／削除など）を早期に固定する必要がある
- 読み上げ中の認識ストップはホスト実装に依存する。読み上げ状態の通知漏れがあると既存仕様を再現できない
- 送信時読み上げと方式Aの切り替え設定はホスト差分になる。二重読み上げにならないよう、設定の意味（排他か独立か）をホスト製品で明確にする必要がある
- クリア反映はホスト差分が残る。スパイクで早期検証が必要
- YYProbe は初回スコープ外のため、両アプリ差分による API 見直しは将来課題として残る
- 配布は SPM で進めるが、ホストへの本番組み込みはテスト後の別判断である
- タイムライン仕様と SDK 仕様を分けないと、受入条件が画面依存のままライブラリに混入する

### 未決のまま残すもの（承認前に潰す議論リスト）

（なし — 本 ADR で挙げた議論ポイントは Decision まで落とした）

## Compliance（以降 PR のチェックリスト）

発言支援ライブラリ関連の PR では、説明文のチェックリストに次を転記し、該当項目を確認する。Issue は採番まで `Refs #TBD`（採番後に置換）。

- [ ] 成果物は **案 B（方式Aまでの発言支援 SDK、UI なし）** である
- [ ] ライブラリに **音声認識クライアントやタイムライン UI を含めない**
- [ ] 製品として勧める読み上げは **方式Aのみ**である（方式Bを既定や推奨にしない）
- [ ] ホスト向け公開面は **入力通知（現在テキスト＋IME 未確定か、等）と最小の結果購読**に閉じている
- [ ] Feature 向けドメインイベント（`events` 相当）や各 Feature 実装を、ホスト必須の公開契約にしていない
- [ ] ホスト View は **表示と入力事実の中継**に留め、読み上げ・効果音のビジネスルールを View に戻していない
- [ ] 読み上げ後の入力クリアは **ライブラリが要求しホストが実行**できる契約である（特定画面構造を前提にしない）
- [ ] 効果音は **既定アセットを同梱**し、未差し替えでも方式Aが完結する
- [ ] 効果音の差し替え API を **初版から**提供する（差し替えは任意。内部アセットパスをホスト必須契約にしない）
- [ ] **Audio Session はホスト専有**とし、ライブラリはカテゴリ設定・アクティブ化を行わない
- [ ] 読み上げ中の音声認識ストップ／終了後の再開は **既存 YY 系アプリ仕様に合わせホストが行う**（ライブラリは読み上げ状態を通知する）
- [ ] 既存の送信時読み上げと方式Aは **併存**し、**設定で切り替え可能**である（ライブラリ導入で送信時読み上げを廃止しない）
- [ ] 初回の組み込み検証・受入対象ホストは **YY文字起こし に限定**する（YYProbe への拡大は初回スコープ外）
- [ ] 公開 API に **特定アプリ名や YYProbe 固有前提を埋め込まない**
- [ ] 配布形態は **Swift Package（ソース配布）** である
- [ ] 本 ADR の決定範囲は **ライブラリとして作ること**までとし、YY文字起こしへの本番組み込み可否はテスト後の別判断である
