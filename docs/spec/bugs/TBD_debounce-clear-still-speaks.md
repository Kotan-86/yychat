## 不具合現象と再現手順（Why）

### 発生している現象

確定テキストを入力したあと、デバウンス完了前に入力をすべて削除しても、削除前の文字列が読み上げられ、spoken 通知とクリア要求が出る。方式Aの「現に残っている確定テキストが 0.5 秒静止したときだけ読む」という期待と食い違う。

### 再現手順

1. ホストから確定テキスト（例:「こんにちは」、IME 未確定でない）を SDK に渡す
2. デバウンス間隔（既定 0.5 秒）が満了する前に、確定テキストを空（または前後空白のみ）にして再度渡す
3. その後デバウンス間隔以上待つ
4. **期待**: 読み上げ・spoken 通知・クリア要求は発生しない
5. **実際**: 手順 1 の文字列が読み上げられ、spoken 通知とクリア要求が発生する

## 修正内容（What）

### 根本原因

空白／空の確定テキスト変化がデバウンス入力から除外されているため、削除後の変化が待機中タイマーをリセットせず、直前の非空テキストのデバウンスが満了して読み上げが走る。

### 修正方針

確定テキストが空または空白のみになった変化もデバウンスの入力として扱い、待機中の読み上げ候補を取り消す。デバウンス満了時点の確定テキストが空または空白のみのときは、読み上げ・spoken 通知・クリア要求を行わない（既存の空白のみ非対象と整合させる）。

## 受入基準（再発防止・回帰テスト）

1. **再現手順の検証**: 上記再現手順を実行したとき、読み上げ・spoken 通知・クリア要求が発生しないこと。
2. **通常のデバウンス確定読み**: 非空の確定テキストを渡し、その後デバウンス間隔以上入力が止まったとき、その文字列が読み上げられ、spoken 通知とクリア要求が出ること。
3. **空白のみ**: 最初から空白のみの確定テキストを渡した場合も、読み上げ・spoken・クリア要求が出ないこと（既存受入の維持）。
4. **影響範囲**: Return／送信相当のみの通知では再読み上げしないこと、読み上げ失敗時は spoken／クリアを出さないこと（既存 SDK 受入の維持）。
